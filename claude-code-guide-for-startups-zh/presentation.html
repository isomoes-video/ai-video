RULE 01 人人都能交付

最懂问题的人，应该能直接交付第一个可工作的解决方案。

连接工具

不是把律师、销售拉进 IDE，而是把 Claude 带进他们每天使用的系统与数据。

展示原型

设置季度评审或专用 Slack 频道，让非技术成员的原型进入正式路线图。

共享 Skills

用设计系统、领域知识与流程规范，让“人人交付”仍保持产品一致性。

边界没有消失：非技术成员负责从 0 到 1，设计师和工程师在专业节点接力。

RULE 03 信任，但要验证

自动化的前提不是“模型很聪明”，而是结果可监控、可审计、可回归。

  • 根目录 CLAUDE.md 写下架构不变量、安全边界与不可妥协项
  • 每次改动跑 golden set 与随机样本，提前发现回归
  • 专家审核模型的推理与修正，所有版本留痕
  • 修复原则，而不是记住单个例子

CAINEX 医疗编码闭环

错误不是 typo，而是合规事件

Agent 处理批次 → 审计员检查代码与推理 → Claude 读取纠正 → 修改版本化指令 → 用 golden set 回测 → 只把难例交给工程师。

“Fix the principle, not the example.”

RULE 04 为重建而设计

模型能力一直在移动，今天的架构很可能半年后就该推倒重来。

Clay：建四遍

每次重建都带着更清晰的需求，第四次才真正知道系统需要什么。

Commure：拆旧也自动化

用 Skill 扫描已全量发布的 feature flags，并行创建删除旧代码的 PR。

Harvey：敢于 Agent-native

新一波模型能力到来时，完整重构平台，而不是守着沉没成本。

原博客图：一个仓库、共享对象库，三个独立 worktree 可同时运行 main、feature 与 hotfix。

低成本重建方法：在隔离 worktree 中跑 v2，与 v1 并列评测，只有新版本胜出才合并。

Figure © Anthropic · 对非平凡重写，先用 --plan 审查路径，再开始改代码。

创业团队的落地清单

本周就能开始

  • 选择一个高频、机械、结果可验证的流程
  • 连接 Claude 所需的代码、数据与协作工具
  • 在根目录记录架构、安全与业务不变量

  • 把团队最佳实践封装成可共享 Skill

规模化之前

  • 建立并持续更新多个 golden eval sets
  • 重要闭环加入独立验证者与人工审核
  • 用 worktree 隔离并行任务与架构重写
  • 把成功条件、最大轮次与回滚写清楚
  • 先内部 dogfood，再决定是否客户产品化
