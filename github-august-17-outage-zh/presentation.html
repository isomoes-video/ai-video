根因是一条容量级联链

01

新流量峰值

Central US 的入口负载超过历史容量包络。

02

Istio sidecar 满载

Pod 达到并发上限，成为最先显现的瓶颈。

03

扩容策略看错指标

策略监控 host service，却没有监控 sidecar 限制。

04

4 台 HAProxy 耗尽 flow

网关认证路径延迟飙升，故障扩散到更多产品。

关键点：高可用节点仍然在线，并不等于它们还有可用的流量处理余量。

重试把局部过载变成正反馈

总请求 = 原始请求 × (1 + 重试)

当失败概率随负载上升时，“再试一次”会制造更多失败，而不是提高成功率。

乐观网关重试继续向内部负载均衡器施压。

延迟响应让客户端误判请求未完成，重复发送。

缺少抖动与预算会让大量调用方同步重试，形成脉冲流量。

补充解释：健康的重试应设置总预算、指数退避、随机抖动，并只针对明确可重试的错误。

04

渐进恢复流量

按站点逐步 ramp up，让调用方先恢复成功。

为什么恢复花了更久

外部噪声：抓取攻击

针对 codeload 端点的多次 scraping attacks 与真实用户流量叠加，使容量判断和恢复更困难。

  • 下载请求单位成本较高
  • 峰值期间更容易争抢连接与带宽
  • 恶意与故障放大流量需要分别识别

内部盲点：监控对象不完整

系统看见 host service 的指标，却没有把 sidecar 与 flow 容量视为同一条端到端路径。

  • 组件健康不代表路径健康
  • 区域切换也必须设置接收上限
  • 恢复操作需要防止客户端继续放大

后续工作：把容量、重试与故障域一起治理

修正扩容策略

把 sidecar 并发与容量纳入 autoscaling。

审计 Istio 限制

检查 request、concurrency 与 scaling 配置。

约束重试行为

复核网关与客户端的预算、退避和抖动。

修复 VS Code

消除放大 Copilot token 流量的潜在循环。

强化区域防护

改进 LB 容量监控与区域 failover safeguards。

真正的韧性，不是“还能重试”，而是过载时能主动减载、隔离并受控恢复。
